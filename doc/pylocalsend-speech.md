## 第 1 页 · 封面

**幻灯片标题：** PyLocalSend

### 大纲要点
- 自我介绍与项目名称
- 一句话说明项目做什么
- 点出技术栈

### 演讲稿

> 大家好，我们今天的展示项目是 **PyLocalSend**，一个面向局域网的文件传输工具。  
>  
> 它的核心思路很简单：发送端在本机登记文件路径，接收端通过命令行或浏览器就能下载；如果老师需要收作业，也可以允许接收端把文件反向上传到发送端电脑。  
>  
> 项目使用 Python 开发，底层是 FastAPI 提供 HTTP 服务，NiceGUI 做 Web 界面，传输过程采用流式读写，尽量降低内存占用。

## 第 2 页 · 章节页（01 / PROBLEM）

**幻灯片标题：** 文件传输的问题，常常不在“能不能传”

### 大纲要点
- 引出真正痛点：成本、步骤、稳定性
- 过渡到下一页的传统方案

### 演讲稿

> 我们先从问题出发。  
>  
> 文件传输这件事，很多时候不是“能不能传”的问题——U 盘能传、网盘能传、聊天软件也能传。真正麻烦的是：**成本高、步骤多、还不稳定**。  
>  
> 接下来我们看几种常见方式各自卡在哪里。

## 第 3 页 · 传统方式的阻力

**幻灯片标题：** 传统方式的阻力

### 大纲要点
- U 盘：硬件依赖、易遗漏
- 网盘：公网中转、隐私与速度
- 聊天软件：体积限制、目录结构差
- 收束到项目目标

### 演讲稿

> 第一种是 **U 盘**。它直观，但要反复插拔，多人轮流用时很麻烦，文件夹里漏几个子目录也很常见。  
>  
> 第二种是 **网盘**。文件要先上传到公网，再让对方下载，速度和隐私都不完全在自己手里。  
>  
> 第三种是 **聊天软件**。发小文件还行，大文件经常有限制，而且文件夹结构基本保不住。  
>  
> 所以我们做 PyLocalSend，就是想把“传文件”这件事变简单——在局域网里，少步骤、少中转、尽量可控。

## 第 4 页 · 传统方案流程图

**幻灯片标题：** 传统方案：先复制到内存

### 大纲要点
- 结合 SVG 讲“两次搬运”
- 发送端读入内存 → 再发给接收端
- 大文件时内存压力大

### 演讲稿

> 这张图是传统方案的典型流程。  
>  
> 发送方先把整个文件读进内存，再通过网络发给接收方，接收方再写入本地。等于文件内容在传输过程中至少被完整处理一遍，**大文件时内存压力很明显**。  
>  
> 如果同一台机器还要同时做别的事，或者文件是几个 GB 的视频、数据集，这种方式就不太友好。

**备注：** 用手指或激光笔沿 SVG 箭头走一遍：发送端 → 内存 → 网络 → 接收端。

## 第 5 页 · PyLocalSend 流程图

**幻灯片标题：** PyLocalSend 方案：边读边发

### 大纲要点
- 对比上一页：流式分片
- 发送端按需读取，不整文件进内存
- 为后面“零拷贝”铺垫

### 演讲稿

> PyLocalSend 的做法不同。  
>  
> 发送端**不会先把整个文件读进内存**，而是按分片从磁盘读取，读一块发一块，接收端边收边写。  
>  
> 你可以把它理解成：文件始终待在原来的磁盘位置上，传输时只是打开一条“水管”，让数据流过去。这也是我们后面会反复提到的**流式传输**思路。

## 第 6 页 · 项目定位

**幻灯片标题：** 项目定位

### 大纲要点
- 发送端共享、接收端下载
- 无账号体系、无公网依赖、不提前复制
- 零安装 WebUI、一服务多接收端

### 演讲稿

> 项目的定位可以概括成一句话：**发送端负责共享，接收端负责下载**。  
>  
> 我们不搞复杂的账号系统，也不依赖公网网盘中转；发送端只是在本地启动一个 HTTP 服务，把已有文件或文件夹“登记”进来。  
>  
> 接收端这边，打开浏览器链接就能下载，**零安装**；一个发送端可以同时服务多个接收端，用 PIN 或独立的 token 链接区分身份。

## 第 9 页 · CLI 使用

**幻灯片标题：** CLI 使用

### 大纲要点
- 适合批量、指定目录、断点续传
- 演示右侧命令（可简略带过）
- gui / upload / ls-remote / download

### 演讲稿

## 第 10 页 · 接收端 WebUI（下载）

**幻灯片标题：** 接收端 WebUI

### 大纲要点
- 单文件：浏览器直接下载
- 文件夹：ZIP 流
- 仅显示已开放项；自动同步

### 演讲稿

> 接收端打开 `/r/令牌` 链接就能进 WebUI，不需要再装 Python。  
>  
> **单文件**由浏览器直接向发送端拉流，保存到浏览器默认下载目录。  
>  
> **文件夹**则由发送端按开放范围实时打包成 ZIP 流，浏览器下载为一个 zip 文件。  
>  
> 页面上只会看到发送端勾选开放过的项目，而且每 2 秒轮询 catalog 版本，发送端改了开放范围，接收端列表会自动刷新，不用手动点刷新。

## 第 11 页 · 接收端浏览器上传

**幻灯片标题：** 接收端浏览器上传

### 大纲要点
- 默认禁止，发送端单独允许
- 「上传文件」标签页 + NiceGUI 组件
- 存放路径规则；不自动进共享列表（下一页会再强调）

### 演讲稿

> 除了下载，我们还做了**反向上传**，适合收作业、收实验数据这类场景。  
>  
> 默认每个接收端都不能上传。发送端在「接收端管理」里对某个接收端点**允许上传**之后，对方页面会多出一个**「上传文件」**标签，用 NiceGUI 的上传组件选文件，支持多文件自动上传。  
>  
> 文件会落到发送端配置的目录下，路径是 `存放根目录/接收端名称/文件名`。根目录可以在设置里改，默认在 `~/.pylocalsend/browser_uploads`。同名文件会自动加时间戳，避免覆盖。  
>  
> 这里要特别说明：**上传成功以后，文件不会自动出现在发送端共享列表里**。老师如果想再发给别人下载，需要自己去「文件传输」里手动注册那条路径。

## 第 12 页 · 下载开放与接收端控制

**幻灯片标题：** 下载开放与接收端控制

### 大纲要点
- 勾选 = grants，可细到子路径
- 禁用 = 停下载 + 停上传 + 中断进行中下载
- 允许上传 / 全部开放 / 自动同步

### 演讲稿

> 这一页把权限控制串起来。  
>  
> **开放勾选**决定接收端能看到什么：可以只开放文件夹里的某几个子目录，状态存在 `download_grants` 表里。  
>  
> **禁用接收端**是一键熔断：新的下载和上传都不行，已经在进行的下载也会被中断；解除禁用后链接恢复正常。  
>  
> 另外还有按接收端开上传、一键全部开放，以及前面说的 catalog 自动同步。整体思路是：共享范围可控、接收端身份可控、传输过程可记录。

## 第 14 页 · 整体架构

**幻灯片标题：** 整体架构

### 大纲要点
- 左：发送端（FastAPI、NiceGUI、SQLite、本地文件）
- 右：接收端（CLI、浏览器、下载目录）
- 中间：HTTP 流、PIN/TOKEN、Range、可选 Upload

### 演讲稿

> 架构上就是两台电脑通过 HTTP 通信。  
>  
> **发送端**跑 SenderService，对外提供 FastAPI 接口；NiceGUI 做管理页和接收端页面；SQLite 存元数据、开放范围和下载日志；真正的文件还在本地磁盘上。  
>  
> **接收端**可以是 CLI 客户端，也可以是浏览器 WebUI。  
>  
> 中间这条链路支持流式传输、PIN 和 token 鉴权、Range 断点续传，以及可选的浏览器上传。注意上传是额外能力，默认关闭。

## 第 15 页 · 文件共享流程

**幻灯片标题：** 文件共享流程

### 大纲要点
- 六步流程走读
- 三个关键词：不复制、不缓存、低内存

### 演讲稿

> 共享一条文件的完整流程分六步：启动服务 → 登记路径 → 元数据写入 SQLite → 接收端拉列表 → 发起下载 → 发送端分片读取并返回。  
>  
> 注册时**不复制**文件，只记路径；下载时**不缓存**整文件到临时目录，而是直接读源文件；读写都按分片进行，所以**内存占用低**，适合大文件。

**备注：** 六格 flow 从左到右快速点完，每格 5～8 秒。

## 第 16 页 · 文件夹下载策略

**幻灯片标题：** 文件夹下载策略

### 大纲要点
- CLI：目录树 + 递归 + 并行/续传
- Web：ZIP 流，不落盘临时包
- 示意图 folder → folder.zip

### 演讲稿

> 文件夹下载，CLI 和 Web 策略不同。  
>  
> **CLI** 会先拿目录树，然后在接收端按相对路径一层层建目录，支持并行和断点续传，适合完整同步。  
>  
> **WebUI** 则把文件夹实时打成 ZIP 流发给浏览器，**不会在发送端先生成一个临时 zip 文件**，省磁盘也省等待。  
>  
> 所以浏览器里你看到的是 `folder.zip`，但发送端磁盘上并没有多出一个压缩包。

## 第 17 页 · 访问控制与记录

**幻灯片标题：** 访问控制与记录

### 大纲要点
- 六条 line-list 各用一句话
- 不必逐条念 API 名称

### 演讲稿

> 安全和可观测性靠这几块。  
>  
> **PIN** 做发送端统一验证；**TOKEN** 给每个接收端独立链接，可禁用、可管上传；**GRANT** 控制哪些路径可见、可下。

>  
> 这些能力组合起来，既方便课堂临时共享，也方便事后查记录。

### 演讲稿

## 第 21 页 · 数据持久化

**幻灯片标题：** 数据持久化

### 大纲要点
- ~/.pylocalsend 下三个文件
- 五张表/配置的用途

### 演讲稿

> 运行时数据放在用户目录 `~/.pylocalsend`。

## 第 24 页 · 当前限制

**幻灯片标题：** 当前限制

### 大纲要点
- 浏览器不能指定任意保存路径
- 默认面向可信局域网
- 上传不自动共享；大文件 Web 上传有内存限制
- CLI vs WebUI 适用场景

### 演讲稿

> 诚实说一下当前限制。  
>  
> 第一，WebUI 下载位置由浏览器决定，不能像 CLI 那样写到任意绝对路径，这是浏览器安全模型决定的。  
>  
> 第二，项目默认面向**可信局域网**，要上公网得自己做端口映射和安全加固。  
>  
> 第三，接收端上传**不会自动共享**；第四，Web 上传要把文件经浏览器读入内存，超大文件更适合 CLI 或本机直接注册路径。  
>  
> 所以我们的结论是：**CLI 适合复杂批量下载，WebUI 适合零安装接收、反向上传和课堂演示**。

## 第 25 页 · 总结（SUMMARY）

**幻灯片标题：** PyLocalSend

### 大纲要点
- 复述核心价值
- 六个关键字各点一下

### 演讲稿

> 最后总结一下。  
>  
> PyLocalSend 让发送端只登记路径，下载时流式读取，尽量降低操作复杂度。  
>  
> 六个关键词：**低成本**——局域网直连；**局域网**——不依赖公网中转；**流式传输**——边读边发；**可管理**——接收端、记录、禁用都可控；**细粒度开放**——勾到哪下到哪；**反向上传**——按需收文件到发送端。  
>  
> 希望这个工具在课堂、实验室里能真正省几步操作。

## 第 27 页 · Q&A

**幻灯片标题：** Q&A

### 大纲要点
- 邀请提问
- 准备 2～3 个常见问题备用

### 演讲稿

> 我们的展示到这里结束，谢谢大家。  
>  
> 欢迎提问。如果被问到下面几类，可以参考回答：  
>  
> **问：和网盘、飞书传文件有什么区别？**  
> 答：我们不做公网存储，数据在局域网直连，发送端完全掌握共享范围和接收端权限。  
>  
> **问：为什么上传不自动共享？**  
> 答：故意分开两条链路——先收到老师电脑，再由老师决定要不要、对谁开放，避免学生误传文件直接暴露给所有人。  
>  
> **问：大文件怎么办？**  
> 答：下载走流式分片；CLI 支持断点续传。上传若很大，建议本机注册路径或后续扩展分片上传。
